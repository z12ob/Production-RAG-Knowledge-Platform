# ADR-005: Use Alembic for database schema migrations

## Status

Accepted on 2026-08-29.

## Context

Changing an ORM class changes Python metadata, not an existing database. Production data must move
through reviewed, ordered schema changes that can be applied consistently across environments. Table
creation during application startup would make release behavior implicit and unsafe to coordinate
across multiple application instances.

## Decision

Use Alembic as the sole schema migration mechanism. Keep revision files in version control, connect
Alembic to the same validated database URL as the application, and expose the SQLAlchemy model
metadata in `alembic/env.py`. The initial reversible revision creates the `knowledge_bases` table and
its constraints. Application startup will not call `create_all`.

## Alternatives

SQLAlchemy `create_all` is convenient for disposable examples but does not describe how an existing
schema and its data should evolve. Hand-maintained SQL scripts provide full control, but Alembic adds
ordered revision history and SQLAlchemy metadata comparison while still allowing handwritten SQL.
An external migration service is unnecessary at the current scale.

## Consequences

Deployments must run `alembic upgrade head` before code that depends on the new schema receives
traffic. Upgrades and downgrades are explicit and reviewable, although a downgrade is not guaranteed
to preserve data and must be assessed per revision. Autogenerated migrations remain drafts that need
human review; model metadata alone is not a deployment plan.
